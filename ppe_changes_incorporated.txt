IMPORTANT: the first 9 knobs above were originally implemented only
inside a PUMAS/MG3-based microphysics variant, which this repo does not
carry (MG2 only, per instruction). They were hand-ported directly onto
the real MG2 code (micro_mg2_0.F90) by locating the analogous formula
in each case (accretion, ice fallspeed, ice effective radius, ice
accretion of cloud droplets, homogeneous-freezing size, ice number cap)
-- this is new code written to match the same pattern, not a mechanical
port of an existing diff. Recommend testing before relying on it for a
production PPE.

Also found (and did NOT reproduce) a real bug in the source this was
ported from: micro_mg_iaccr_factor and micro_mg_accre_enhan_fact were
applied there as whole-array multiplications (e.g. "psacws = psacws *
factor") sitting inside a per-vertical-level do-loop, which compounds
the factor across levels on every loop iteration once it deviates from
1.0 -- invisible at the default value of 1.0, which is presumably why
it went unnoticed. This port applies both multiplications scoped to
the current level ("psacws(:,k) = ...") instead.

6. MMPPE mandatory-21 parameter port (see MMPPE-info/MMPPE.md)
------------------------------------------------------------
Goal: implement the 21 "mandatory" parameters from the AeroCom Multi-Model
PPE (MMPPE) protocol. Ported by hand-mapping each ECHAM/HAM-named protocol
parameter onto the equivalent CAM6/MG2/MAM4/ZM process, using the CAM7
reference tree (/glade/work/addisus/sandboxes/CAM_github/CAM) as a guide for
where a similar knob was already added there.

6a. Already covered by existing knobs -- no code changes made:
  emi_du         -> dust_emis_fact              (stock CAM6)
  wetdep_ic      -> sol_facti_cloud_borne       (stock CAM6; default 1.0
                                                  matches protocol default)
  activ_aero     -> microp_aero_npccn_scale     (added in commit 5, above)
  activ_cwturb   -> microp_aero_wsub_scale /
                     microp_aero_wsubi_scale    (added in commit 5, above)
  micro_ccraut   -> micro_mg_autocon_fact       (added in commit 5, above)
  conv_cprcon    -> zmconv_c0_lnd / zmconv_c0_ocn (stock CAM6)

6b. New namelist knobs added this round, all defaulting to no change in
    behavior:

  Emission-rate scale factors (mo_srf_emissions.F90, chemistry.F90):
    srf_emis_scale_so2_ant, srf_emis_scale_so2_bb   (emi_ant_so2, emi_bb_so2)
    srf_emis_scale_bc_ant,  srf_emis_scale_bc_bb    (emi_ant_bc,  emi_bb_bc)
    srf_emis_scale_oc_ant,  srf_emis_scale_oc_bb    (emi_ant_oc,  emi_bb_oc)
    srf_emis_scale_dms                              (emi_dms)
  New public srf_emis_scale_readnl() in mo_srf_emissions.F90, called from
  chemistry.F90's chem_readnl (parallel to dust_readnl). Applied via a new
  get_srf_emis_ppe_scale(species, filename) function at the point
  emissions(m)%scalefactor is set, matched by species name + an
  anthro/'_bb_' substring tag in the emission-dataset filename (CMIP6-style
  datasets already split anthro vs. bb into separate files per species).
  BC/OC mass-emission scaling is also applied to their independently
  prescribed companion number-emission files (num_a4_bc/num_a4_oc/
  num_a4_bb/num_pom_bb, species 'num_a4') so the assumed emitted particle
  size is unaffected by a pure mass-rate perturbation -- this was a
  deliberate design choice (confirmed with user), not an incidental default.
  Primary sulfate (so4_a1/so4_a2/num_a1/num_a2) is NOT scaled by the SO2
  knobs -- only the SO2 gas-phase emission is scaled, consistent with the
  protocol treating primary-sulfate emission as a separate, much smaller
  pathway it doesn't otherwise call out.

  Sea salt accumulation/coarse split (seasalt_model.F90, aero_model.F90):
    seasalt_emis_scale_accum, seasalt_emis_scale_coarse
    (emi_ss_acc, emi_ss_coa)
  Applied on top of the existing global seasalt_emis_scale. In MAM4's
  3-bin scheme (accum, aitken, coarse), the coarse-mode scale applies only
  to the last bin (ibin==nslt); the aitken bin is deliberately left
  unscaled by either new factor (per user decision) -- only the
  accumulation bin (ibin==1) responds to seasalt_emis_scale_accum.

  Ice-to-snow autoconversion rate scale (micro_mg_utils.F90, micro_mg2_0.F90,
  micro_mg_cam.F90):
    micro_mg_iautocon_fact (micro_ccsaut)
  ice_autoconversion()'s previously hardcoded 180s autoconversion timescale
  is now scaled by this factor (multiplies nprci, and prci inherits the
  scaling through nprci). Threaded through micro_mg_init exactly like the
  existing micro_mg_autocon_fact (liquid autoconversion) knob.
  IMPORTANT: ice_autoconversion() is also called from zm_microphysics.F90
  (ZM's own optional convective-cloud microphysics, zmconv_microp) -- that
  call site now passes a literal 1.0_r8 (unscaled) rather than the new
  namelist knob, since micro_ccsaut is scoped to MG2 stratiform
  microphysics only, not ZM's convective microphysics.

  ZM entrainment rate (zm_conv.F90, zm_conv_intr.F90):
    zmconv_dmpdz (conv_entrpen), default -1.0e-3 m-1
  Replaces the previously hardcoded ocean/general entrainment rate
  (dmpdz) in parcel_dilute(); the land-specific dmpdz_lnd stays hardcoded
  at -1.e-3, matching how CAM7's own zmconv_dmpdz knob is implemented
  (CAM7 also leaves its land entrainment hardcoded).

7. MMPPE OAT output-variable diagnostics (see MMPPE-info/OAT_variable_mapping.txt)

  Two reference files were added to MMPPE-info/ (not part of the build):
  cloud-top-calculation.F90 (pseudocode for the AeroCom/aci-baseline
  cloud-top diagnostic algorithm that MMPPE.md's "Cloud-top calculation"
  note points to) and output_aerocom_aie.F90 (a full legacy E3SM module
  implementing that same algorithm plus many other diagnostics from a
  different, older AeroCom AIE experiment -- not all of it relevant here).
  Two concrete changes came out of comparing these against the current
  codebase:

7a. ndrop.F90: added a 7th CCN supersaturation bin, CCN7 (S=0.3%), to
  give MMPPE's ccns.3/ccncol.3 (and the equivalent CCNS_0.300/
  CCN_BURDEN_0.300/CCN_BL1_0.300/CCN_0.300 variables in the other output
  tables) an exact match -- CAM6's native bins were previously fixed at
  0.02/0.05/0.1/0.2/0.5/1.0% (CCN1..CCN6) with no 0.3% bin, so these were
  approximated via CCN4 (0.2%). Appended as CCN7 rather than inserted in
  sorted order, so CCN1..CCN6 keep their existing supersaturation
  identities. See the "MMPPE OAT NOTE" comment above ndrop.F90's
  psat/supersat/ccn_name declarations. Not on by default (same as
  CCN1/2/4/5/6 -- only CCN3 is); add via fincl to get it in history output.

7b. micro_mg_cam.F90: added overlap-weighted cloud-top diagnostics --
  ACTREL_OVL, ACTREI_OVL, ACTNL_OVL, ACTNI_OVL, FCTL_OVL, FCTI_OVL --
  ADDED ALONGSIDE the existing ACTREL/ACTREI/ACTNL/ACTNI/FCTL/FCTI
  (not replacing them), specifically so the two methods' output can be
  compared directly. The existing fields stop scanning at the FIRST
  cloudy level below top_lev; the new _OVL fields instead accumulate
  contributions from every cloud-top-exposed layer using a
  maximum-random cloud-overlap assumption, adapted from
  output_aerocom_aie.F90's cloud_top_aerocom subroutine (itself
  following cloud-top-calculation.F90) -- the protocol-referenced
  method, and a materially more correct calculation than the
  first-cloudy-layer approach when clouds are broken/multi-layered.
  Uses the same grid-mean (not in-cloud) convention as the existing
  ACTNL/ACTREL fields: divide by FCTL_OVL/FCTI_OVL to recover true
  in-cloud cloud-top values. Directly relevant to MMPPE's cdnc_incl_ct/
  ND_INCL_CT, CDR_CT, and ICR_CT variables (see
  MMPPE-info/OAT_variable_mapping.txt and
  MMPPE-info/6hourly_variable_mapping.txt).
  Scope explicitly deferred (per user decision, not attempted this
  round):
    - Porting other output_aerocom_aie.F90 diagnostics that don't map to
      a current MMPPE.md variable: cloud-top CCN at a fixed
      supersaturation, cloud-top pressure/temperature (ptop/ttop -- could
      potentially upgrade CTH from its current APPROX mapping if revisited,
      by converting a liquid-phase-weighted cloud-top pressure to height),
      column-integrated autoconversion/accretion (note: MG2 already
      outputs the 3D rates natively as PRAO/PRCO, so this would be a cheap
      new vertical-integration addfld, not a port), and the various
      "before microphysics" (*bf) burden diagnostics.
    - CBH (cloud-base height, currently NONE-BEST in the mapping files):
      the reference material only provides a cloud-TOP algorithm; a
      bottom-up analog was not attempted since it would be an original
      extrapolation beyond what's actually in the reference code, not a
      verified port.
  Not yet validated against real model output -- like the rest of this
  branch, needs a control run to confirm ACTNL_OVL/FCTL_OVL etc. produce
  sane values before relying on them (see "No compile/run test" below).

7c. radiation.F90 (rrtmg): added a new ANGSTRM output field (Angstrom
  exponent, 400nm-700nm), for angstrm550_865 and the equivalent
  ANG_440nm_670nm/ANG_550nm_865nm variables in the other output tables.
  A third reference file, MMPPE-info/radiation.F90 (a legacy E3SM
  radiation driver), was added by the user after finding that
  output_aerocom_aie.F90's own 'angstrm'/'aerindex'/'aod400'/'aod700'
  fields were dead code -- addfld'd and pbuf-registered but never
  actually computed or outfld'd anywhere in that file. MMPPE-info/
  radiation.F90's do_aerocom_ind3 block (around its line 1365) has the
  real, working formula: angstrm = (ln(aod400)-ln(aod700)) /
  (ln(0.700)-ln(0.400)), with aod400/aod700 column sums of per-band
  aerosol optical depth at RRTMG SW bands idx_sw_diag+1/idx_sw_diag-1.

  Checking this against the current codebase turned up that
  src/physics/rrtmg/radiation.F90 ALREADY computes the exact per-level
  inputs needed -- rd%aer_tau400/550/700 (rad_out_t type, populated at
  the aer_tau550/400/700 assignment right before the rad_rrtmg_sw call)
  -- but nothing in the standard (non-SPCAM) build path ever summed or
  output them; the only existing consumer is src/physics/spcam/
  spcam_drivers.F90 (sum(rd%aer_tau550(i,:)) etc., SPCAM-only). So this
  was a cheap, low-risk addition: sum the already-computed rd%aer_tau400/
  aer_tau700 over levels and apply the exact reference formula, no new
  radiative-transfer computation needed. Changes:
    - rad_out_t (radiation.F90): added angstrm(pcols) field.
    - radiation_init: addfld('ANGSTRM', ...), guarded to icall==0 only
      (not extended to the '_d1'.._d10' diagnostic-radiation-call
      variants -- matches the reference code's own "only for
      climatology run" restriction, not this file's usual per-icall
      pattern used for FSNT/SWCF/etc.).
    - radiation_tend: computes rd%angstrm right after the aer_tau550/
      400/700 assignment, icall==0 only, with the same nnite/idxnite
      night-column fillvalue masking already used elsewhere in this file
      (e.g. tot_cld_vistau) -- day-only, consistent with AODVIS/AODUV/
      AODNIR's own day-only convention in modal_aer_opt.F90.
    - radiation_output_sw: outfld('ANGSTRM', ...), icall==0 only.
  NOT an exact match to angstrm550_865/ANG_550nm_865nm's requested
  550-865nm pair -- CAM/RRTMG's SW bands don't bracket 865nm at all (see
  band-edge math in the mapping-file notes); 400-700nm is the pair the
  reference implementation actually used and validated in a real AeroCom
  submission, so it was ported as-is rather than picked to match the
  MMPPE band pair. AOD400/AOD700 themselves were deliberately NOT
  exposed as their own history fields (kept as local scalars only) --
  MMPPE.md doesn't request them, only the Angstrom exponent itself; adding
  them would be unrequested scope. Not on by default; add via fincl.
  Like 7a/7b, not yet validated against real model output.

  - radiation.F90 (rrtmg): added FSUTOAC (clear-sky upwelling SW at TOA),

  fed from prco_grid/prao_grid -- note this confirms PRCO=autoconversion,

  Like 7a-7c, not yet validated against real model output.

7e. radiation.F90 (rrtmg): added a second Angstrom exponent field,
  ANGSTRM_550_865, alongside (not replacing) the 400-700nm ANGSTRM added
  in 7c -- a closer wavelength match to angstrm550_865/ANG_550nm_865nm.
  RRTMG's 14 SW bands (radconstants.F90) have no boundary at 865nm; this
  uses band 10 (441-625nm, idx_sw_diag -- the same band AODVIS already
  uses for "550nm") and band 8 (778-1242nm, idx_sw_diag-2) for "865nm".
  Band 8 was chosen over band 9 (625-778nm, idx_sw_diag-1, the next band
  down and the band the 400-700nm ANGSTRM's "700nm" side already uses)
  because 865nm falls entirely outside band 9's range but inside band 8's,
  and band 8's log-wavelength center (sqrt(778*1242)=983nm) is roughly
  twice as close to 865nm in log-space as band 9's center
  (sqrt(625*778)=697nm) is. Same rad_out_t/radiation_init/radiation_tend/
  radiation_output_sw structure as ANGSTRM, same icall==0-only and
  day-only (fillvalue at night) convention, same choice to keep AOD550/
  AOD865 as local scalars rather than their own history fields (matching
  the AOD400/AOD700 scope decision in 7c). Not on by default; add via
  fincl. Like 7a-7d, not yet validated against real model output.

8b. kappa_so4: NEW code, in 3 files plus namelist registration. SO4's
  hygroscopicity (kappa) is read from a physprop netCDF lookup table at
  runtime (phys_prop.F90's pio_get_var(nc_id, vid, physprop%hygro_aer))
  -- the same kind of "baked into a data file" situation that got
  rad_bc_ni/rad_oc_ni deferred in section 6c -- but more tractable here
  since hygro_aer is consumed at a small number of well-defined call
  sites via rad_cnst_get_aer_props(...,hygro_aer=...), not spread through
  a whole radiative-optics pipeline.
    - New namelist variable kappa_so4 (real, group="zmconv_nl" for
      build-namelist purposes only -- see below for why -- default -1,
      a sentinel meaning "no override, physprop table value unchanged").
      MMPPE lists this parameter as Abs (an absolute value), not Rel, so
      a non-negative kappa_so4 REPLACES (does not scale) SO4's
      hygro_aer, for both SO4-bearing MAM4 modes (so4_a1 accumulation,
      so4_a2 aitken -- confirmed these are MAM4's only SO4-carrying
      modes; there is no so4 in the coarse/a3 or primary-carbon/a4
      modes).
    - ndrop.F90 (the main/most frequently called stratiform activation
      path, loadaer()): added the kappa_so4 module variable, a new
      public ndrop_readnl(nlfile) subroutine (called from chemistry.F90's
      chem_readnl, parallel to srf_emis_scale_readnl -- confirmed no
      circular dependency: ndrop.F90 does not use chemistry.F90), and the
      override itself in loadaer's per-species loop (added aername to its
      existing rad_cnst_get_aer_props call to identify so4_a1/so4_a2).
    - zm_conv_intr.F90 (ZM's own, separate convective-aerosol activation
      path, in zm_conv_init's aerosol-property init loop -- this path
      caches all species' spechygro into an array ONCE at init, not per
      timestep, so the override only needed adding in one place): added
      kappa_so4 to the EXISTING zmconv_nl namelist/readnl (a small,
      low-risk addition to already-established infrastructure) and the
      same aername-based override logic in its aerosol-property init
      loop.
    - Why kappa_so4 is registered under group="zmconv_nl" even though
      it's not a ZM convection parameter: microp_aero.F90 was the more
      semantically obvious home (it already hosts activ_aero/
      activ_cwturb's knobs) but already `use ndrop`, so ndrop.F90 using
      it back would be a circular module dependency. zmconv_nl was
      already fully wired in zm_conv_intr.F90 and has no such issue.
      ndrop.F90 independently declares its own `namelist /zmconv_nl/
      kappa_so4` and reads the same named group from the same atm_in
      file as zm_conv_intr.F90 does -- a standard, valid Fortran pattern
      (multiple compilation units reading the same named group), chosen
      specifically to avoid adding any new module-to-module dependency.
    - Explicitly NOT touched, per user decision: hetfrz_classnuc_cam.F90
      has its own separate, independently hardcoded spechygro_so4 =
      0.507_r8 parameter, used for heterogeneous ice nucleation
      classification -- a different physical process from droplet
      activation, using its own independent constant. kappa_so4 does not
      override it. Document this scoping decision if kappa_so4 is
      revisited -- it would be an easy thing for a future change to
      accidentally "complete" without realizing it was deliberately
      excluded.
  Verified via test/unit/namelist_ppe/test_mandatory_ppe_namelist.sh
  (new case added there) that kappa_so4 registers correctly and
  round-trips through build-namelist; the actual Fortran override logic
  (species-name matching in ndrop.F90/zm_conv_intr.F90) is NOT covered by
  that test (it only drives build-namelist, doesn't compile/run CAM) and
  is, like everything else on this branch, not yet validated against
  real model output.

  Both parameters added to scripts/oat_parameters.csv (categories
  "recommended"/"optional" respectively) with PLACEHOLDER low/high
  values, same convention as the mandatory-21 rows there.

9. rad_bc_ni, rad_oc_ni -- BC/OC imaginary refractive index at 550nm
  (the 2 of the mandatory-21 MMPPE parameters deferred in section 6c,
  revisited per explicit user clarification on how the protocol intends
  wavelength-dependent species to be handled).

  Per user clarification, the protocol value is defined at 550nm; for a
  species whose imaginary refractive index varies by SW band, all SW
  wavelengths are scaled by the same factor (new_value / value_at_550nm),
  preserving the species' native spectral shape. LW is explicitly ignored
  (not important for aerosol extinction per the protocol clarification).
  Reference implementation given was ICON-HAM's cni(1:Nwv_sw_tot,iradbc)
  *= (bc_rad_ni / cni(Nwv_sw+1,iradbc)) -- adapted here since CAM's
  RRTMG-SW discretization has no dedicated extra reference-wavelength
  array slot the way ICON-HAM's cni does; idx_sw_diag (radconstants.F90,
  =10, the 441-625nm band) is used as the in-band 550nm equivalent --
  this is already CAM's own established stand-in for "550nm" (used the
  same way elsewhere in phys_prop.F90 for a SULFATE visible-band
  diagnostic, and in this branch's ANGSTRM/AODVIS diagnostics).

  No CAM6/CAM7 knob previously existed for either parameter -- the
  imaginary refractive index is baked into the physprop netCDF lookup
  tables read at runtime (phys_prop.F90), not a Fortran constant. Checked
  this branch's default BC/OC physprop files directly: BC's imaginary
  refractive index (bcpho_rrtmg_c100508.nc, aername BCPHO) is spectrally
  flat at 0.79 across all 14 SW bands; OC's (ocpho_rrtmg_c130709.nc,
  aername OCPHO for POM; ocphi_rrtmg_c100508.nc, aername OCPHI for SOA)
  varies ~15x band-to-band (0.005-0.079) but is numerically IDENTICAL
  between the POM and SOA files in this branch's defaults -- so
  rad_oc_ni scales both consistently from the same starting data.

  - phys_prop.F90: new public module reals rad_bc_ni (default 0.79) and
    rad_oc_ni (default 0.0056650108), defaulting to the actual values
    baked into this branch's default physprop files (not a sentinel --
    per user decision, since this PPE will use the same physprop lookup
    tables throughout, an unperturbed namelist reproduces the unmodified
    data via a scale factor of ~1). New scale_refindex_im_sw() helper
    rescales a species' refindex_aer_sw(:) imaginary part at every SW
    band by (new_ni_550 / refindex_aer_sw(idx_sw_diag)'s current value),
    leaving the real part untouched. Called from bulk_props_init() --
    the single point downstream of refindex_aer_init() (which has
    already populated refindex_aer_sw) that all three optics-init code
    paths BC/OC actually use (insoluble_optics_init for BCPHO/OCPHO,
    hygroscopic_optics_init for OCPHI) funnel through, keyed on
    physprop%aername so one hook covers both species without
    duplicating the call in three places.
  - rad_constituents.F90: rad_bc_ni/rad_oc_ni registered in the existing
    rad_cnst_nl namelist (use-associated from phys_prop, since
    rad_cnst_readnl already runs before rad_cnst_init calls
    physprop_init -- guaranteed correct read-before-use ordering without
    a new readnl/module dependency).
  - namelist_definition.xml / namelist_defaults_cam.xml / build-namelist:
    registered under group="rad_cnst_nl", add_default() called
    unconditionally (not gated on rrtmg, since the MAM4 physprop files
    these scale are radiation-package-agnostic).
  - test/unit/namelist_ppe/test_mandatory_ppe_namelist.sh: moved from
    the DEFERRED (expected-absent) block into the main CASES
    (implemented, round-trip-checked) block; mandatory-implemented count
    updated 17 -> 19, deferred count 4 -> 2 (emi_cmr_ff/emi_cmr_bb only).
  - scripts/oat_parameters.csv: added as mandatory-category rows
    (PLACEHOLDER low/high, per this file's existing convention) with
    notes on the CAM-baked-in vs. protocol default discrepancy (BC:
    0.79 vs. protocol's 0.71; OC: ~0.00567 vs. protocol's 0.0055).

  Not covered by any test: the actual Fortran scaling logic
  (scale_refindex_im_sw) is not exercised by
  test_mandatory_ppe_namelist.sh (that test only drives build-namelist,
  doesn't compile/run CAM) and, like everything else on this branch, is
  not yet validated against real model output.
